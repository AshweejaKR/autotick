PROJECT SUMMARY
================================================================================

AutoTick is a modular, broker-independent framework supporting Live, Paper,
Backtest, and Replay modes through one codebase.

Core rules:

- Strategies generate signals and do not select modes or brokers.
- ProviderFactory selects market data, account, execution, and session timing.
- Broker SDK code stays inside broker adapters.
- Models and provider contracts stay normalized.
- CalendarSessionManager owns the run's single-exchange calendar.
- RiskManager owns sizing and risk limits.
- TradeManager owns order, position, completed-trade, and report triggering flow.
- Optional components are added only in their planned phase.

CONFIGURATION BEHAVIOR
================================================================================

config/default.yaml is the only default YAML.

Relative credential, CSV, persistence, and report paths resolve from the YAML
file directory before validation.

production secrets:
- AngelOne secrets remain in angelone_keys.env.
- required values: API_KEY, CLIENT_ID, PASSWORD, TOTP_SECRET.
- missing/unreadable files, duplicate keys, missing keys, and blank values fail.
- secret values and file contents are never logged.
- Paper validates AngelOne secrets only when broker access is needed.
- Live requires persistence, reconnect, market-hours gate, and logging enabled.

reports:
- reports.enabled enables completed-trade CSV export and summaries.
- reports.user_id is optional and may be any user-selected label.
- when reports.user_id is blank, AngelOne CLIENT_ID is used when available.
- reports.output_dir selects the report directory.
- no timestamp is added to report filenames.

REPORTING FLOW
================================================================================

One report trade means one completed ENTRY + EXIT pair.

When a filled EXIT closes a managed position:

TradeManager
  -> locate the matching filled ENTRY trade
  -> calculate completed-trade P&L
  -> ReportManager.record()
  -> append strategy trade CSV if exit_trade_id is new
  -> recalculate strategy summary from accumulated CSV
  -> append combined trade CSV if exit_trade_id is new
  -> recalculate combined summary from accumulated CSV

Strategy filenames:

broker_userid_strategy_mode_trades.csv
broker_userid_strategy_mode_summary.csv

Combined filenames:

broker_userid_mode_trades.csv
broker_userid_mode_summary.csv

Combined scope:
- same broker
- same user ID
- same mode
- all strategies using that identity

Trade CSV fields:
- exit_trade_id
- entry_trade_id
- strategy
- broker
- user_id
- mode
- symbol
- exchange
- quantity
- entry_price
- exit_price
- pnl
- entry_time
- exit_time

Summary metrics:
- completed_trades
- wins
- losses
- win_rate_pct
- gross_profit
- gross_loss
- net_pnl
- average_pnl
- best_trade
- worst_trade

Report behavior:
- trade CSV is append-only for unseen completed trades.
- duplicate exit_trade_id values are skipped.
- summary CSV is overwritten with recalculated accumulated metrics.
- reporting uses Python standard-library csv only; no pandas or chart package.
- reporting errors are logged and do not undo an already completed trade.

PERSISTENCE AND RECOVERY
================================================================================

- SQLite state is stored in one configured .db file.
- profiles are isolated by mode, broker, exchange, strategy, and symbols.
- Live and Paper recover managed state before strategy setup.
- Paper restores simulated account/trade state.
- unknown broker orders/holdings stay unmanaged and block duplicate entries.
- unresolved broker writes trigger reconciliation and safe shutdown.
- Backtest and Replay start fresh and save final state for later use.

RECONNECT
================================================================================

- Live and broker-backed Paper use ReconnectManager when enabled.
- temporary read/network failures retry with capped exponential backoff.
- authentication recovery tries refresh before full login.
- subscriptions restore before reconciliation and strategy resume.
- broker writes are never automatically retried.

RISK AND TRADE MANAGEMENT
================================================================================

RiskManager:
- caps configured quantity using capital, risk percentage, price, and stop loss.
- filled ENTRY increments daily trade count.
- max-trade limit activates the kill switch.
- exposes stop-loss, target, trailing-stop, and daily-limit helpers.
- keeps the validated runtime config used by report setup.

TradeManager:
- owns order-state transitions.
- tracks normalized orders, positions, trades, and exit levels.
- reconciles known broker records.
- monitors stop-loss, target, and trailing-stop exits.
- closes positions only after filled exits.
- calculates realized P&L for completed exits.
- triggers Phase 28 reporting only for completed ENTRY + EXIT pairs.

ORDER STATE MACHINE
================================================================================

NEW -> VALIDATED -> SUBMITTED
SUBMITTED -> OPEN / PARTIAL / FILLED / REJECTED / CANCELLED / EXPIRED
OPEN -> PARTIAL / FILLED / CANCELLED / EXPIRED
PARTIAL -> FILLED / CANCELLED / EXPIRED

Only a FILLED ENTRY consumes the daily trade limit.

POSITION STATE MACHINE
================================================================================

NO_POSITION -> ENTRY_PENDING -> OPEN -> EXIT_PENDING -> CLOSED

DESIGN PRINCIPLES
================================================================================

1. Correctness before speed.
2. Simplicity before complexity.
3. Maintainability before cleverness.
4. One normalized contract per provider capability.
5. Broker SDKs remain inside broker adapters.
6. Strategies remain focused on market conditions and signals.
7. RiskManager and TradeManager own risk and trade workflow.
8. One CalendarSessionManager owns the single-exchange schedule and time.
9. Add optional components only in their planned phase.
10. Keep README.md, PLAN.md, and this guide synchronized.
