AUTOTICK - ARCHITECTURE & IMPLEMENTATION GUIDE

PROJECT SUMMARY
================================================================================

AutoTick is a modular, broker-independent framework supporting Live,
Paper, Backtest, and Replay modes through one codebase.

- Same Strategy generates BUY/SELL/HOLD signals in every mode.
- TradingEngine uses provider interfaces only and remains mode-neutral.
- ProviderFactory switches market data, account, execution, and session timing.
- Live/Paper use broker data; Backtest/Replay share HistoricalProvider.
- engine/market_session.py contains only CalendarSessionManager.
- CalendarSessionManager owns real-time, fast, or replay timing and session checks.
- Broker components share one authenticated session through SessionPool.
- EventDispatcher provides one event flow across all modes.
- TradeManager owns order, position, trade, exposure, and P&L workflow/state.
- RiskManager independently validates risk and position sizing.

Deferred until required: StrategyManager, MarketCache, generic BaseProvider,
and separate ReplayProvider.

Rules:
- Add __init__.py files when packages are implemented.
- Keep one factory.py and one historical.py.
- Keep Strategy base under strategy/.
- Do not add replay_provider.py or replay_clock.py.
- Create optional files only in their implementation phase.
- Add indicators only when a strategy requires them.
- TradeManager/RiskManager own order-state, position-state, trailing, cooldown,
  duplicate-entry, re-entry, target, stop-loss, quantity sizing, and risk workflow.
- Strategy stays focused on market conditions and signal generation.
- SignalValidator is engine-owned and performs structural checks only; it does not perform risk checks.

ARCHITECTURE FLOW

Startup Flow
============

main.py
  -> Load and validate configuration
  -> Initialize logging
  -> ProviderFactory creates ProviderBundle for selected mode
  -> SessionPool creates/reuses broker session when required
  -> Initialize CalendarSessionManager, providers, engine, and Strategy
  -> Restore state when enabled
  -> TradingEngine.start()

Trading Loop (per tick/bar)
===========================

MarketDataProvider -> EventDispatcher -> Indicators -> TradingEngine context
-> Strategy -> Signal -> SignalValidator -> RiskManager -> TradeManager
-> ExecutionProvider -> TradeManager updates state -> Persistence/Reports

High-Level Architecture
=======================

Configuration -> ProviderFactory -> ProviderBundle
ProviderBundle -> MarketDataProvider / AccountProvider / ExecutionProvider
ProviderFactory -> CalendarSessionManager -> TradingEngine
TradingEngine -> Indicators -> Strategy -> SignalValidator -> RiskManager
RiskManager -> TradeManager -> ExecutionProvider -> TradeManager
TradeManager -> Persistence / Reports

================================================================================
MODE SWITCHING (Provider Factory)
================================================================================

Mode     | Market Data        | Execution | Account   | Session Timing | Purpose
---------|--------------------|-----------|-----------|----------------|-----------------
Live     | Broker Feed        | Broker    | Broker    | Real time      | Real trading
Paper    | Broker Feed        | BrokerSim | BrokerSim | Real time      | Paper trading
Backtest | HistoricalProvider | BrokerSim | BrokerSim | Fast advance   | Fast testing
Replay   | HistoricalProvider | BrokerSim | BrokerSim | Replay speed   | Timed replay

ProviderBundle contains market_data, account, execution, and calendar_session.
Strategy never reads the active mode. New brokers require
adapter registration only; new modes require ProviderFactory wiring only.

SimpleStrategy
- on_initial_setup() fetches the latest completed daily bar through MarketDataProvider.
- Previous-day close comes from that bar.
- BUY when LTP > previous-day close * 1.005.
- Otherwise return no signal.
- Target and stop loss come from configuration outside Strategy.
- Duplicate-entry and re-entry decisions remain outside Strategy.

ORDER STATE MACHINE
================================================================================

NEW -> VALIDATED -> SUBMITTED -> OPEN
                              +-> PARTIAL -> FILLED
                              +-> FILLED / REJECTED / CANCELLED / EXPIRED

Broker statuses are normalized. Transitions are validated, timestamped,
idempotent, and persisted.

POSITION STATE MACHINE
================================================================================

NO_POSITION -> ENTRY_PENDING -> OPEN -> EXIT_PENDING -> CLOSED

TradeManager owns position state, exposure, and realized/unrealized P&L.
Startup recovery reconciles stored positions with broker positions.

DESIGN PRINCIPLES
================================================================================

1. Same Strategy across all modes.
2. Provider substitution through dependency injection.
3. Broker SDKs remain inside broker adapters.
4. All time and session behaviour comes from CalendarSessionManager.
5. One CalendarSessionManager supports real-time, fast, and replay timing.
6. Events and models are normalized before reaching Strategy.
7. Order/position state transitions are explicit and validated.
8. Configuration controls mode, broker, calendar, and risk.
9. Production behaviour is recoverable, observable, and auditable.
10. Optional components are added only when required.

Required production controls: position/order/daily-loss limits, stop loss,
targets, trailing stop, square-off, duplicate-order prevention, kill switch,
reconnect, token refresh, state recovery, audit trail, and Paper soak testing.

SESSION LIFECYCLE
================================================================================

Broker session:
Provider -> SessionPool -> reuse healthy session or login/refresh -> cache
-> share with Account/MarketData/Execution -> reconnect/resubscribe on failure
-> safe logout during shutdown.

Market session:
initialize() -> configure mode and check calendar -> on_market_open()
-> on_initial_setup() -> on_tick()/on_bar() -> validate signal
-> on_order_filled() -> should_square_off() -> on_market_close()
-> checkpoint -> engine shutdown.

Session timing:
- Live/Paper: wall-clock time.
- Backtest: advance directly through historical events.
- Replay: advance historical events at configured replay speed.
- TradingEngine always uses the same CalendarSessionManager methods.
